# DataMiner package-backed Automation solution reference

This is the single authority for the shared lifecycle of a DataMiner package
project that contains an Automation project. Load it whenever a task combines
`dataminer-package-project` with `dataminer-automation-project`, including DOM
model packages.

The domain agent owns the model or business rules. `dataminer-automation-core`
and `dataminer-automation-scripting` own normal Automation runtime and C#
guidance. This reference owns the project shape, package wiring, install-hook
boundary, Catalog metadata, and package validation. Do not copy those rules
into an agent or another skill; link back here instead.

## Authority and required references

| Concern | Authority |
|---|---|
| Package/project scaffolding, package contents, install hook, Catalog metadata, and package lifecycle | This reference |
| Normal Automation entry point, abort behavior, script parameters, dummies, and exit states | `dataminer-automation-core` |
| Automation C# implementation | `dataminer-automation-scripting` |
| DMSScript XML | `dataminer-automation-xml` |
| Skyline templates, SDK, package tools, and version selection | `dataminer-sdk` |
| Catalog README and manifest hygiene | `dataminer-catalog-hygiene` |
| Domain model, schema, stable IDs, and reconciliation policy | The selected domain skill or agent |

Before scaffolding, load `dataminer-sdk`, this reference, and the domain
authority. Load `dataminer-automation-core` and
`dataminer-automation-scripting` for the provisioning Automation project; do
not infer the package install entry point from the normal `Run(IEngine)`
contract.

## Scaffold the solution

Use the official templates. Read the installed template help before running
the commands because options and generated signatures can change:

```text
dotnet new install Skyline.DataMiner.VisualStudioTemplates
dotnet new dataminer-package-project --help
dotnet new dataminer-automation-project --help
```

Inspect the repository before scaffolding for `.sln`/`.slnx`, `.csproj`,
`Directory.Build.*`, `global.json`, instructions, and existing package or
provisioning code. Preserve an existing SDK policy. Never hand-write a
substitute for an available official template, and never use a console or
plain class-library project in place of a DataMiner artifact.

The default multi-project shape is:

```text
<repository-root>\<Stem>.sln
<repository-root>\<Stem>.Package\<Stem>.Package.csproj
<repository-root>\<Stem>.Provisioning\<Stem>.Provisioning.csproj
<repository-root>\<Stem>.Tests\<Stem>.Tests.csproj
```

The package, provisioning, and test projects are siblings. Create the
solution at the repository root and add all three projects (for example with
`dotnet sln "<Stem>.sln" add ...`). Build the skeleton before adding domain
logic, then rebuild after every structural move.

### Package project wiring

The package project includes sibling SDK projects through
`PackageContent\ProjectReferences.xml`, not through an MSBuild
`<ProjectReference>` item. Paths are relative to the package project:

```xml
<ProjectReferences xmlns="http://www.skyline.be/projectReferences">
  <ProjectReference Include="..\*\*.csproj" />
  <ProjectReference Exclude="..\<Stem>.Tests\<Stem>.Tests.csproj" />
</ProjectReferences>
```

Verify the generated file and the installed SDK behavior rather than
resolving the wildcard by visual intuition. The package must include the
provisioning project and must not package the test project by accident.

### Package project properties

The package template scaffolds these properties. Adjust them rather than
replacing the generated project:

| Property | Purpose |
|---|---|
| `DataMinerType` | `Package` for the package project, `AutomationScript` for the script project |
| `GenerateDataMinerPackage` | Produces the `.dmapp` on build |
| `MinimumRequiredDmVersion` | Blocks installation below the declared DataMiner version |
| `Version` / `VersionComment` | Package version and description |
| `CatalogPublishKeyName` | Name of the environment variable or user secret containing the Catalog key, never the key itself |

The package project may also contain `CatalogInformation`,
`PackageContent` (`ProjectReferences.xml`, `CatalogReferences.xml`,
`CompanionFiles`, `Dashboards`, and `LowCodeApps`), and `SetupContent` for
files needed only during installation. Setup files are reached through the
template-generated installer API, such as
`installer.GetSetupContentDirectory()`.

## Package install hook

The `dataminer-package-project` template scaffolds the install script and its
XML manifest. Edit the generated files; do not hand-write a replacement
`Install.xml`. The scaffolded `Run` method is not the package-install entry
point.

Keep the exact signature generated by the installed template. Sources differ
on `Engine` versus `IEngine`, so the template and a compile probe are the
authority. The package-install shape is:

```csharp
[AutomationEntryPoint(AutomationEntryPointType.Types.InstallAppPackage)]
public void Install(IEngine engine, AppInstallContext context)
{
    engine.Timeout = TimeSpan.FromMinutes(10);

    var installer = new AppInstaller(Engine.SLNetRaw, context);
    installer.InstallDefaultContent();

    // InstallDefaultContent() must run first: it installs the provisioning
    // script that the sub-script call below invokes.
    var provisioning = engine.PrepareSubScript("<Stem>.Provisioning");
    provisioning.Synchronous = true;
    provisioning.StartScript();

    // Verify the template-specific sub-script failure surface and fail the
    // installation explicitly when provisioning did not succeed.
}
```

The generated project normally supplies `Skyline.AppInstaller`,
`Skyline.DataMiner.Automation`, `Skyline.DataMiner.Net.AppPackages`, and the
`Skyline.DataMiner.Core.AppPackageInstaller` package reference. Keep the
template's package versions and references unless the repository has a
deliberate version policy. The legacy
`<Param type="ref">SLAppPackageInstaller.dll</Param>` pattern is for
hand-built DIS solutions, not SDK package projects.

Every install and upgrade runs the hook again. The hook must therefore be
idempotent: install default content first, invoke provisioning only through
the verified template API, and surface the object and operation when a
provisioning call fails. Do not seed business records, run destructive
migrations, or change stable IDs from the install hook. If the solution
declares `provisioningTrigger: "manual-script"`, omit the sub-script call and
document the manual Automation script that the operator runs after install.

Probe every uncertain install API inside the target project, including the
attribute, parameter types, `AppInstallContext`, `InstallDefaultContent()`,
sub-script invocation, and failure result. Reflection over installed DLLs is
not a substitute for a compile probe.

## Catalog information

`<Stem>.Package\CatalogInformation\` is user-facing and is included in the
Catalog metadata archive when `GenerateDataMinerPackage` is enabled. Replace
the template placeholder before reporting the package complete:

1. Rewrite `CatalogInformation\README.md` for an operator, describing the
   package's business outcome, prerequisites, and what gets installed.
2. Remove `CatalogInformation\Images\wip.png` and any reference to it.
3. Set the manifest `type`, human-readable `title`, tags (at most five), and
   `source_code_url` when known. Preserve an existing GUID in `id`; changing
   it creates a different Catalog item.

The README must accurately describe the generated package, state that install
and upgrade are safe and do not duplicate or erase existing records, and use
the actual `MinimumRequiredDmVersion` and permissions. Domain-specific
packages may override `type` and add domain prerequisites, but the shared
Catalog hygiene rules remain here. Load `dataminer-catalog-hygiene` when
editing the metadata.

Use this structure unless the repository has an established Catalog
documentation convention:

```markdown
# <Human-friendly package name>

## About

Two to four sentences in plain language: what this package gives the user,
which problem it solves, and which business objects it contains.

## Key Features

- **<Short bold label>**: what the user can now do.
- **<Short bold label>**: what the user can now do.

## Prerequisites

- DataMiner <MinimumRequiredDmVersion> or higher.
- <Any permission or dependency needed to install or use it.>

## What gets installed

- <Plain-language list of the data structures or capabilities created.>
```

Do not list GUIDs, field descriptor types, section names, class names, or C#
types in an operator-facing README. Regenerate it when the package contents or
install behavior changes. Images are optional; if one is referenced, store it
under `CatalogInformation\Images\` and link it relatively.

## Build, package, and deployment boundaries

Use the repository's normal build command and run `dotnet build` after
scaffolding and after meaningful structural or project-file changes. Keep
warnings visible; do not add `NoWarn` to make a generated solution appear
clean. Parse edited XML, JSON, and project files, and inspect test discovery
output. `no tests discovered` is a coverage gap, not a pass.

If packaging is requested, inspect the produced `.dmapp` archive and verify
that it contains the package manifest/default content, install hook, and
provisioning script. Report these statuses separately:

| Status | Meaning |
|---|---|
| Source | Files were generated or edited |
| Build | The solution compiled and analyzers passed |
| Package | The artifact was created and, when requested, inspected |
| Deployment | An operator or an explicitly authorized tool installed it |
| Runtime | Behavior was exercised on a compatible DataMiner System |

Building a package is not deployment evidence. DIS publish, manual `.dmapp`
installation, Catalog publication, and Catalog deployment are distinct
operations. Document the applicable route and required permissions without
claiming it ran unless it actually did. Never place Catalog keys, DataMiner
credentials, or tokens in source or logs. The domain agent's hard rules
control whether any operational command may be executed; a design-first
agent must keep these routes documentation-only.

### Deployment routes to document

- **DIS publish for development iteration**: with DataMiner Integration Studio
  configured for a target DMA, publish the Automation Script XML from the
  editor. DIS builds and installs the package temporarily. Refer to this as
  an IDE with the DIS extension; credentials remain in DIS settings.
- **Manual install**: installing the built `.dmapp` on the DataMiner host is
  distinct from publishing it to the Catalog. `SLNetClientTest` is a fallback
  route; do not recommend System Center for app packages.
- **Catalog CI/CD**: use the template workflow for shared packages, store the
  organization key in a repository secret such as `DATAMINER_TOKEN`, and
  document the Catalog scopes required to register and download versions.
  Pushes may create pre-release versions; a GitHub release can cut a proper
  release.
- **Catalog deployment**: a cloud-connected system, linked account, and the
  *Modules > System configuration > Agents > Install App packages* and
  *Modules > Automation > Execute* permissions are required.
- **One-off Catalog operations**: `dotnet publish` on the package project
  publishes to the Catalog, not to an Agent. `dataminer-package-deploy`
  deploys a Catalog version to an Agent. Do not confuse either operation with
  DIS *Publish*, which targets an Agent.

Set `MinimumRequiredDmVersion` from the highest feature gate used by the
domain model or provisioning code. Keep package version and
`VersionComment` changes explicit in the plan.
