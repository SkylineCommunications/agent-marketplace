# First-release connector review matrix

## Contract metadata and authority

- **Matrix version:** `phase2-matrix-v1`
- **Source:** the external OneNote checklist export named `first-release-connector-review-checklist.txt`.
- **Source version:** **unknown**.
- **Source date:** **unknown**.
- **Source path convention:** the source path is external and is recorded as
  `OneNote/<checklist>/first-release-connector-review-checklist.txt`; repository traceability is
  `section/domain/<source-id>@<occurrence-id>` plus the source line span in `notes`. The raw export
  is intentionally not stored in this repository.
- **Policy owner:** the **OneNote checklist maintainer** owns and ratifies coverage and release-gate
  policy. Row owners execute evidence; they do not silently change checklist policy.
- **First-release opt-in:** this matrix is inactive unless the release explicitly opts in to a
  first-release review and records that decision. Applicability must be recorded as
  `NOT_APPLICABLE` with evidence when a conditional row does not apply.
- **Authority:** the OneNote checklist controls *what is covered* and the proposed gate. Technical
  validity comes from the protocol schema reference, the official protocol validator, SDK/DIS/QAOps
  guidance and results, and vendor documentation/MIB/API evidence as applicable. These sources
  validate a row; they do not silently rewrite its coverage or gate.
- **Conflict policy:** if the checklist requirement conflicts with schema, validator, SDK/DIS/QAOps,
  vendor, or safety evidence, report **`CONFLICT`**, cite both sources and the exact location, block
  any invalid or unsafe fix advice, and escalate to the checklist maintainer and the relevant
  technical authority. Never resolve a conflict by guessing.
- **Evidence hygiene:** redact credentials, tokens, customer/device identifiers, and other sensitive
  values from snippets, logs, screenshots, and external references.

## Maintenance

The OneNote checklist maintainer owns revisions to coverage and release-gate policy. The current
source intentionally has no version/date metadata; keep both values as `unknown` until the source
process changes. `SCRXXX` labels are accepted as supplied and do not require canonical replacement.

When the external checklist changes:

1. Preserve the new checklist outside the repository using the execution-time file convention.
2. Rebuild the occurrence-level inventory, retaining source sections, line spans, duplicate IDs,
   form fields, and manual `Other Remarks` channels.
3. Add, retire, or revise section/domain-qualified matrix rows without silently reusing a key for a
   different rule.
4. Reconcile `existing`, `enhance`, and `new` coverage against `review-checklist.md`; do not duplicate
   normal-baseline findings.
5. Reconfirm `applies_if`, check kind, evidence recipe, owner, release gate, feedback/snippet recipe,
   post-fix validation, and `conflict_handling` for every changed row.
6. Run `evals/validators/first-release-review-matrix-contract.ps1` and the normal connector-review
   regression before changing any first-release scenario expectations.
7. Record the source change, maintainer decision, and affected scenarios in the relevant skill,
   reviewer, or evaluation changelog.

## Coverage and relationship to `review-checklist.md`

`review-checklist.md` is the existing finite reviewer baseline. This matrix is a source-traceability
and evidence layer; it is not a second copy of that checklist.

- **`existing` (38 occurrences):** the domain is already represented in the baseline. Reuse that
  check and record this source occurrence as traceability; do not create a second check.
- **`enhance` (100 occurrences):** the baseline domain exists, but this source occurrence adds a
  narrower rule, evidence recipe, owner, or gate. Record only the delta and link the review result
  to the baseline check.
- **`new` (27 occurrences):** the occurrence is not represented in the baseline. Run it only when
  the explicit first-release opt-in and `applies_if` permit it, then have the maintainer ratify it
  before making it a standing gate.

The matrix deliberately omits all 50 section/subsection/table headings (7 section headings, 36
subsection headings, and 7 table headers) and all 330 form fields from the automatic row set.
`Other Remarks`, `Remark (1st)`, and `Developer Comments` remain manual/reference channels: retain
the source occurrence for traceability where it has an ID, but never turn its free-text content into
an automatic PASS/FAIL check. The 129 automatic/evidence-bearing rows are operational check rows
(58 actionable, 70 conditional, and one technical duplicate/reference row); their `check_kind`
determines static, tool, runtime, human, or external evidence. The 36 manual/reference occurrences
are 35 `Other Remarks` rows plus one duplicate/reference remark.

## Row contract

The rows below are one JSON object per source-ID occurrence. A row has exactly these fields:

| Field | Type and allowed values | Contract |
|---|---|---|
| `key` | non-empty string matching a section/domain-qualified internal key | Stable unique key; use the normalized inventory key. |
| `source_ids` | one-element array of `SCR` source tokens | Token form is the exact supplied source ID plus occurrence context: `<source-id>@<occurrence-id>`, for example `SCR1007@occ-0010`. `SCRXXX` remains exactly `SCRXXX`. |
| `section/domain` | non-empty string | `<source section> / <domain> (source lines <start>-<end>)`; preserves location without reproducing headings as rows. |
| `applies_if` | non-empty string | Explicit applicability test, including the evidence needed to mark a conditional row `NOT_APPLICABLE`. |
| `coverage` | `existing` \| `enhance` \| `new` | Relationship to `review-checklist.md`; see the coverage rules above. |
| `check_kind` | `external` \| `human` \| `mixed` \| `static+domain` \| `static` \| `fixture/runtime` \| `tool` | Evidence modality; it is not permission to skip a required technical authority. |
| `evidence_recipe` | non-empty actionable string | What to inspect/run, the target, the evidence to capture, and the applicability decision. |
| `default_severity` | `critical` \| `high` \| `medium` \| `low` \| `info` | Proposed default only; the maintainer may ratify a different policy. |
| `release_gate` | `required` \| `advisory` \| `human-signoff` | Proposed gate, subject to maintainer ratification and first-release opt-in. |
| `owner` | `Connector author` \| `Connector author / DVE owner` \| `Connector author / vendor or platform liaison` \| `Connector release owner / Catalog-DCP administrator` \| `Feature owner / connector author` \| `QA/QAOps test operator / connector author` \| `Reviewer` \| `UI reviewer / connector author` | Person/team accountable for closing or signing off the row. |
| `authority` | ordered array of `onenote-checklist`, `protocol-schema`, `protocol-validator`, `sdk-dis-qaops`, `vendor-docs`, `catalog-dcp`, `qaops-runtime`, `device-fixture`, `reviewer`, `human-ui`, or `tool-output` | First item is the checklist authority for coverage; remaining items are validity evidence. |
| `conflict_handling` | `block-unsafe-fix-and-escalate` \| `preserve-reference-and-escalate` | Technical rows block unsafe fixes on conflict; manual/reference rows preserve the note and escalate. |
| `feedback_mode` | `combined-evidence` \| `domain-finding` \| `external-evidence` \| `human-review` \| `manual-remark` \| `runtime-test` \| `static-finding` \| `tool-result` | Determines how the recipe is reported. |
| `feedback_template` | non-empty string | Must support the feedback rules below and identify the row occurrence. |
| `snippet_recipe` | non-empty string | Exact file/element/line, screen, command output, log, or external record to attach; redact sensitive data. |
| `validation_after_fix` | non-empty string | Repeat the relevant check and state the post-fix evidence required. |
| `notes` | non-empty string | Must retain occurrence ID, source line span, normalized title/classification, coverage basis, and the attached source text; duplicate/reference handling is noted here. |

## Feedback and result rules

- **`FAIL`:** identify the problem, exact file/element/screen and line or record location, current
  snippet, why it matters, the correction (or state that a conflict blocks advice), the owner, and
  the post-fix validation.
- **`PASS` / `NOT_APPLICABLE`:** concise confirmation with the evidence reference; for
  `NOT_APPLICABLE`, state the applicability fact that was checked.
- **`UNVERIFIED` / `BLOCKED`:** name the missing evidence or prerequisite and give an actionable
  instruction to obtain it or unblock the test, including the responsible owner.
- **`CONFLICT`:** cite the OneNote source and the conflicting schema/validator/SDK/DIS/QAOps/vendor
  or safety source, identify the exact locations, and explicitly block an invalid or unsafe fix.
- Manual/reference rows use `REMARK` feedback and a disposition, never an automatic PASS/FAIL.
