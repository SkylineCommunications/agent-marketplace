# Pre-Completion Checklist

Before finishing **any** XML authoring task, explicitly verify each item and fix failures **in the same response**:

- [ ] **SNMP write behavior**: Every requested scalar write has a matching read parameter and an explicit SET behavior. Prefer `snmpSetAndGet="true"` on the write `<Param>`; use another SET pattern only when justified by the requirement. Do not invent writable OIDs or controls.
- [ ] **SNMP scalar groups**: Count direct `<Param>` references in every SNMP group; no group exceeds 10. Split 11 reads at one cadence into groups of 10 and 1. Decide `multipleGet` independently per group: scalar-only groups with two or more scalar reads have `<Content multipleGet="true">`, while singleton and table groups omit it (**multipleGet on groups CANNOT be used for groups with table parameters in it**). Each SNMP table has its own group.
- [ ] **Timer-driven polling and action priority**: Routine polling groups are scheduled by their timers; do not use after-startup actions to poll data that will be retrieved through a timer (the after-startup chain can still be used for one-time initialization). Use `<Time initial="true">` when an immediate first poll is required. Use `execute next` only for an explicit immediate-priority event; use `execute` for ordinary action-triggered group execution.
- [ ] **Multi-tier polling cadence across all connection types**: Static, asset, capability, and rarely changing configuration data (system description, manufacturer, model, serial number, firmware/software version, phase/port counts, static metadata) are segregated into dedicated slow poll groups/sessions and scheduled on a slow timer (10m–1h, `<Time initial="true">`). Fast timers (10s–60s) poll only dynamic operational metrics, telemetry, and tables. Applicable to SNMP, HTTP, Serial, and all other connector types.
- [ ] **Duration & Time measurement formatting (`options="time"`)**: Any parameter measuring elapsed time, remaining run time, uptime, timeout, or duration in seconds uses `<Measurement><Type options="time">number</Type></Measurement>` for automatic `hh:mm:ss` notation in the UI.
- [ ] **XML comment hygiene**: The complete `protocol.xml` contains no explanatory, documentation, TODO, FIXME, debug, workaround, or design-note comments. Preserve only copyright comments and justified `SuppressValidator` wrappers that directly surround the affected element and state a specific reason.
- [ ] **General page exists**: At least one scalar parameter has `<Page>General</Page>` in its `<Positions>`. Listing `"General"` in `pageOrder` alone is NOT sufficient.
- [ ] **RTDisplay on every displayed table**: Every `<Param>` with `<Type>array</Type>` shown on a page has `<Display><RTDisplay>true</RTDisplay><Positions>...</Positions></Display>`.
- [ ] **RTDisplay on every displayed scalar**: Every `<Param>` with `<Type>read</Type>` that has a `<Positions>` block **MUST** have `<Display><RTDisplay>true</RTDisplay></Display>`. **If the total count of `<RTDisplay>true</RTDisplay>` elements in the XML is 0, you have missed RTDisplay on ALL displayed parameters.** Count the `<RTDisplay>true</RTDisplay>` occurrences and verify the count is ≥ the number of parameters that have `<Positions>` blocks.
- [ ] **Table column params: RTDisplay YES, Positions NEVER**: Every table column param MUST have `<Display><RTDisplay>true</RTDisplay></Display>` but **NEVER** a `<Positions>` block. **Count-based verification**: Count the total number of `<Positions>` elements in the XML. The expected count equals (number of displayed table array params) + (number of displayed scalar params). Column params **never** own a `<Positions>` element — if your total `<Positions>` count exceeds this expected value, the excess are inside column params. Find every excess `<Positions>` block inside a column param's `<Display>` and remove it.
- [ ] **SNMP blocks present** (SNMP connectors): **EVERY** `read` scalar and `array` parameter **MUST** have an `<SNMP>` block — **NEVER omit it**. Column parameters need `<SNMP><OID>...</OID></SNMP>`. **MANDATORY COUNT VERIFICATION**: Count the `<SNMP>` elements in the XML. If the count is 0 for an SNMP connector, you have omitted SNMP blocks on **ALL** parameters — add `<SNMP>` blocks to every `read` scalar and `array` parameter before finishing. The count of `<SNMP>` blocks must be ≥ the number of `read` scalar params + `array` params.
- [ ] **SNMP OID type attribute and block-child scan** (SNMP connectors): Scan **every `<OID type="...">` attribute** in the XML — the only valid values are `complete`, `auto`, `composed`, `wildcard`. `id` is an optional `<OID>` attribute, not an `OID@type` value. **NEVER** use SNMP data type names (`integer`, `octetstring`, `gauge`, `gauge32`, `counter`, `counter32`, `timeticks`, `ipaddress`, etc.), SNMP operation names (`Get`, `GetNext`, `GetBulk`), or direction names (`read`, `write`) — each is an **XSD ERROR**. Also scan every `<SNMP>` block for invalid child elements: **NEVER** place `<GetNext/>` or `<GetBulk/>` inside a parameter's `<SNMP>` block. ❌ `<OID type="id">`, `<OID type="integer">`, `<OID type="octetstring">`, `<SNMP><GetNext/></SNMP>` → ✅ `<OID type="complete">1.3.6.1.2.1.1.3.0</OID><Type>timeticks</Type>`
- [ ] **`<LengthType>next param</LengthType>` in every SNMP parameter** (SNMP connectors): **EVERY** SNMP parameter — scalars, table columns, **and write params** — **MUST** have an `<Interprete>` block containing `<LengthType>next param</LengthType>`. Verify by counting: the number of `<Interprete>` elements must equal the number of SNMP `<Param>` elements (reads + writes + table columns).
- [ ] **`volatile` table decision**: Use `volatile` only when the table has no alarm monitoring, `save` columns, foreign keys, DCF usage, or DVE rows. If expected row additions/deletions exceed 7 changes/minute or 10 000 changes/day on one element, the docs require `volatile`; if the same table also needs an incompatible feature, stop and redesign or split the data model rather than emitting a contradictory table. **NEVER** write `options=""`; omit the attribute when no options apply.
- [ ] **First `<Group>` in `<Groups>` is a `poll` group** (SNMP connectors): DataMiner selects the **first defined `<Group>`** element as the ping group. Verify that it has `<Type>poll</Type>` and references at least one SNMP scalar parameter. An "After Startup" `<Type>poll action</Type>` group placed first causes MAJOR "Ping group for 'snmpv2' connection is not a 'snmpv2' poll group" and RTEs.
- [ ] **pageOrder consistency** (bidirectional): **EVERY page name referenced in ANY parameter's `<Positions><Page>` element MUST appear in `pageOrder`** — a page present in `<Positions>` but absent from `pageOrder` causes MAJOR validator errors ("The specified page 'X' does not exist"). Conversely, every page listed in `pageOrder` must have at least one parameter positioned on it. Fix: collect the unique set of `<Page>` values from all `<Positions>` blocks and verify each one appears in `pageOrder`.
- [ ] **WebInterface page present**: `pageOrder` contains `Webinterface#http://[Polling Ip]/` for non-virtual connectors. Added as the last entry after a `-----` separator. **NEVER** add a `<WebInterface>` XML element.
- [ ] **NamingFormat uses separator-based PID references — NEVER `displayColumn` attribute, NEVER `naming=` in `<ArrayOptions options>`**: **NEVER** use the `displayColumn="N"` attribute on `<ArrayOptions>`. ❌ `<ArrayOptions index="0" displayColumn="1">` → ✅ `<ArrayOptions index="0"><NamingFormat>,1002</NamingFormat>`. Every table's `<NamingFormat>` uses the separator-based format with at least one bare parameter ID. **Also verify that no `<ArrayOptions>` element has a `naming=` token in its `options` attribute** — remove it and add/correct `<NamingFormat>,pid</NamingFormat>` as a child.
- [ ] **Table naming**: Every `<Param type="array">` `<Name>` starts with a **lowercase letter**. Derive it from the MIB OBJECT-TYPE descriptor (e.g. `tx21BucInfoTable`, `tx21BucAlarmTable`, `tx21BucSensorTable`), not from the uppercase SEQUENCE type name (e.g. `Tx21BucInfoEntry`). Strip `Table` and keep the result camelCase (`tx21BucInfo`, `tx21BucAlarm`, `tx21BucSensor`). ❌ `<Name>Tx21BucInfo</Name>` → ✅ `<Name>tx21BucInfo</Name>`.
- [ ] **Table column naming**: Each column `<Name>` is camelCase `tableNameColumnName`, where the prefix exactly matches the table's `<Name>`. Removing a redundant `Table` suffix is recommended but not required. When duplicate column descriptions occur in different tables, disambiguate them with the table description or a clear abbreviation in parentheses.
- [ ] **All `<Name>` elements are camelCase — NEVER uppercase first letter**: For every `<Param>` verify that its `<Name>` starts with a **lowercase letter**. Scan ALL params including write params, internal params (AfterStartup), table array params, and column params. Common standalone violations: ❌ `Hostname` → ✅ `hostname`; ❌ `SoftwareVersion` → ✅ `softwareVersion`; ❌ `SystemDescription` → ✅ `systemDescription`; ❌ `SystemName` → ✅ `systemName`; ❌ `SystemUptime` → ✅ `systemUptime`. **Single-word device-property names and multi-word device-identity parameters at PID 1–10 and system-info params at PID 100–999 are the prime violation sources.** If any `<Name>` begins with uppercase, correct it — each violation is a separate MINOR NamingConventions finding.
- [ ] **Multi-table page layout — no overlapping table positions**: For every page with more than one table array param, verify that each table has a **unique Row** (0, 1, 2 …). ❌ Multiple tables all at `<Row>0</Row><Column>0</Column>` → silently overlap. ✅ Tables stacked: Row 0, Row 1, Row 2 …
- [ ] **No orphaned parameter content**: After every `</Param>` closing tag, the next element is either another `</Param>` or a `<Param id="X">` opening tag.
- [ ] **`<Information><Subtext>` on every `<Param>`**: Count every `<Param>` block (scalars, **table array params**, write params, table columns, dummy/internal). Every single one must contain `<Information><Subtext>`. If the count of `<Information>` elements does not match the count of `<Param>` elements, add the missing subtexts before finishing. **Table array params (`<Type>array</Type>`) are the most commonly forgotten.** Do a complete pass: for each `<Param>` lacking `<Information><Subtext>`, add `<Information><Subtext>Brief semantic description</Subtext></Information>` immediately after `<Description>`. Subtext should describe the parameter in plain language for operators; never include SNMP OIDs or low-level technical information.
- [ ] **Units or 2.9.7 suppression on every `number` param**: For every parameter with `<Measurement><Type>number</Type></Measurement>`, make an explicit decision: add `<Display><Units>X</Units></Display>` or wrap `<Display>` with `<!-- SuppressValidator 2.9.7 <reason> -->`. **NEVER leave a number param with neither Units nor a 2.9.7 suppression.** Common reason: `Dimensionless count, no unit applicable`; `Index parameter, no unit applicable`.
- [ ] **Alarm monitoring on valid parameters**: All valid operational health, status, and telemetry parameters (battery capacity %, remaining run time, voltages, currents, power, frequencies, status enums, link states, error rates) MUST have `<Alarm><Monitored>true</Monitored>` with sensible default thresholds (or justified `SuppressValidator 2.5.1` when nominal values depend on installation/grid context or device defaults are unstandardized). Only non-alarmable parameters (write parameters, dummy parameters, table array containers, index PKs, display keys, RTDisplay=false intermediates, static asset information, and volatile tables) omit `<Alarm>`. Every `<Alarm>` block that is present explicitly starts with `<Monitored>true</Monitored>` (or `<Monitored>false</Monitored>` if intentionally unmonitored).
- [ ] **Discrete parameters with numeric backend for pre-known values**: Every parameter representing pre-known values (enumerations, states, modes, statuses, boolean conditions) MUST be implemented as a discrete parameter (`<Type>discreet</Type>`, or `<Type>togglebutton</Type>` for 2-state booleans) with a numeric backend (`<Interprete><Type>double</Type></Interprete>`). The numeric backend ensures the parameter can be alarmed and trended. The displayed text in `<Discreets><Discreet><Display>` must provide clear, operator-friendly text for end users. Never use raw string parameters for pre-known states.
- [ ] **Range or 2.11.1 suppression on every displayed scalar `number` param**: For every non-column scalar with `<Measurement><Type>number</Type></Measurement>` and `<RTDisplay>true</RTDisplay>`, make an explicit range decision: add `<Range><Low>X</Low><High>Y</High></Range>` or suppress 2.11.1 for genuinely unbounded params. **NEVER write an empty `<Range />` or `<Range></Range>` tag** — empty Range = separate WARNING. ❌ `<Range />` → WARNING; ❌ missing `<Range>` entirely → MINOR; ✅ `<Range><Low>0</Low><High>100</High></Range>`.
- [ ] **`<Triggers>` and `<Actions>` sections**: Include and populate these sections when the connector implements corresponding execution logic. When no such logic exists, omission and empty sections are both schema-valid; follow the existing connector convention.
- [ ] **VendorOID is Skyline-assigned**: Verify `<VendorOID>` matches `1.3.6.1.4.1.8813.2.<number>`. Do not use the device vendor's IANA enterprise/sysObjectID OID, the bare Skyline root, or a placeholder. Ask for the assigned connector OID when it is unknown.
- [ ] **HTTP Session and Header attributes**: Every `<Session>` has an `id`; `name` is optional, and `key` is not a valid Session attribute. Every request `<Header>` has its required `key` attribute; `pid` is optional. ❌ `<Session id="1" key="Get Status">` → ✅ `<Session id="1" name="Get Status">`; ❌ `<Header pid="50" />` → ✅ `<Header key="Authorization" pid="50" />`.
